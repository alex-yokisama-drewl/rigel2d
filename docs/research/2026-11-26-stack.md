# What Rigel2D is built on: language, GPU abstraction, UI toolkit

**Researched:** 2026-11-26 · **Feeds:** the stack decision in `docs/stack.md` (currently an empty
template) · **Verdict:** Rust, with wgpu as the GPU abstraction and egui (via `egui-wgpu`) as the
UI toolkit, on winit — and Live's render surface as a separate winit+wgpu window with no UI
toolkit attached to it at all.

## How evidence is marked

Every claim below carries one of these. The distinction is load-bearing: this project has been
bitten before by an API's shape being mistaken for a documented guarantee.

| Mark | Means |
|---|---|
| **[primary]** | Read in the library's own source or its reference documentation, linked |
| **[reported]** | A third party's measurement or report, not reproduced here |
| **[inferred]** | Reasoned from the API's shape. Nothing documents it and nothing was observed |
| **[unknown]** | Could not be established within this budget. Says so, and says what would settle it |

Nothing here was **observed** — no code was built or run. Every "it works" claim is primary or
inferred, never measured. That is the largest single weakness of this document.

## Verdict

**Rust + wgpu + egui + winit**, with a split-window architecture.

Three things decided it.

**wgpu creates pipelines eagerly and bgfx does not.** `wgpu-hal`'s Vulkan backend calls
`vkCreateGraphicsPipelines` synchronously inside `create_render_pipeline`, so every pipeline a
puppet can reach is a thing the runtime creates by name, at load, before the first presented
frame. bgfx's Vulkan backend instead hashes the render state inside `submit()`, looks it up in a
pipeline state cache, and calls `vkCreateGraphicsPipelines` on a miss — pipeline creation *is*
the frame loop, with no public API to force it earlier. That is I5 violated by construction, and
it removes bgfx. The web-technology option inherits the opposite problem from the other side:
WebGPU's own guidance is to use `createRenderPipelineAsync` *because* the synchronous form blocks
on compilation, which means the implementation, not Rigel2D, decides when compilation happens.

**egui's test harness reads an AccessKit tree, headlessly, and that is the shape criterion 3
needs.** `egui_kittest` drives a UI with no window and queries it through AccessKit: filter by
role or label, then read `bounding_box()`, `role()`, `label()`, `is_focused()`, `is_disabled()`,
`is_hidden()` off the node. Bounding-box intersection — the generating case in
`.claude/rules/testing.md`, a hotspot under a persistent strip — is a plain assertion over two
`bounding_box()` results. Dear ImGui's Test Engine gives rects and IDs but has no accessibility
concept at all, which fails the roles-and-names half of criterion 3 outright; Iced's `iced_test`
finds widgets by the text they contain and little else; Masonry's harness is the right shape but
sits under a framework that calls itself experimental.

**Rust makes the per-frame counters cheap and the frame loop naturally allocation-free.**
`docs/requirements/platform.md` demands a per-frame *heap allocations* counter and a
*name resolutions must be zero* counter. In Rust a counting `GlobalAlloc` shim makes the first
exact and free, and there is no collector whose pause could appear in a 99th-percentile 8 ms
budget. D's garbage collector is the inverse: zero allocation is reachable with `@nogc` and
`GC.disable`, but the ecosystem pushes against it and a stop-the-world mark over a
hundred-megabyte heap is the exact stutter the percentile budget exists to prevent.

**Slint was the serious runner-up and lost on coupling, not on capability.** Its `ElementHandle`
testing API is the best of any candidate here — accessible role, label, value, enabled, position,
size, computed opacity, layout kind, and `@testable` properties that can surface a resolved
colour, all against a testing backend that needs no windowing system. It loses on three things
taken together: its wgpu interop is gated behind `unstable-wgpu-NN` feature flags pinned to one
wgpu major version, which couples Studio's viewport upgrade schedule to Slint's; it brings its
own renderer (femtovg or Skia) alongside wgpu, so the editor would carry two GPU renderers
against a 2 GB budget; and GPLv3-or-pay licensing constrains criterion 8, where egui's
MIT/Apache-2.0 does not. Keep Slint as the named fallback if the egui gap below proves fatal.

### The architecture the verdict implies

This is not a detail — it is how I2 stops being a thing to remember and starts being a thing that
cannot happen.

- **Live's render surface** is a bare winit window with a wgpu surface on it, transparent and
  undecorated, with no widget toolkit linked into its draw path. "Nothing but rendered puppet
  content ever reaches the render surface" then holds because there is no mechanism by which
  anything else could: the toolkit does not own that window.
- **Live's control surface** and **all of Studio** are egui on a separate window, sharing the
  wgpu device through `egui-wgpu` so the editor viewport is a paint callback into the same
  device rather than a second renderer.
- **The counters live above wgpu.** The runtime emits its own frame command stream, derives every
  per-frame counter from it, and submits to wgpu as a separate step. See criterion 2 — this is
  forced, not chosen.

## Evidence

### 1. No pipeline compilation or GPU resource creation in the frame loop

| Abstraction | Pipelines created eagerly? | |
|---|---|---|
| wgpu | Yes | `create_render_pipeline` calls `vkCreateGraphicsPipelines` directly |
| Vulkan, directly | Yes | `vkCreateGraphicsPipelines` is the application's call to make |
| sokol_gfx | Yes | `sg_make_pipeline` is an explicit creation call |
| Qt RHI | Yes | `QRhiGraphicsPipeline::create()` is explicit, and ordered against its bindings |
| bgfx | **No** | Created inside `submit()` on a state-hash cache miss |
| WebGPU in a browser shell | Implementation's choice | Spec guidance is to use the async form *because* the sync form blocks |

**wgpu — eager. [primary]** In `wgpu-hal`'s Vulkan backend, `create_render_pipeline` contains
`.create_graphics_pipelines(pipeline_cache, &vk_infos, None)` inside a
`profiling::scope!("vkCreateGraphicsPipelines")`, with the cache handle taken from
`desc.cache.map(|it| it.raw).unwrap_or(vk::PipelineCache::null())`. The same function obtains a
compatible render pass at `let raw_pass = self.shared.make_render_pass(compatible_rp_key)?;` and
passes it into the pipeline info. So the expensive part — shader compilation and pipeline state
object creation — happens when Rigel2D asks for it.
([wgpu-hal vulkan/device.rs source, wgpu-hal 30.x as served by docs.rs, read 2026-11-26](https://docs.rs/wgpu-hal/latest/src/wgpu_hal/vulkan/device.rs.html))

**wgpu — but two object kinds are still created lazily inside the frame. [primary]**
`wgpu-hal`'s Vulkan `DeviceShared` holds
`render_passes: Mutex<FastHashMap<RenderPassKey, vk::RenderPass>>`, and `CommandEncoder` holds
`framebuffers: FastHashMap<FramebufferKey, vk::Framebuffer>`. The module documentation says
"Render passes are cached on the device and kept forever" and that framebuffers "are removed when
any of the image views (they have) gets removed." The source's own module docs and the field
placement disagree about where framebuffers live, which is worth knowing before relying on either.
([wgpu-hal vulkan/mod.rs source, read 2026-11-26](https://docs.rs/wgpu-hal/latest/src/wgpu_hal/vulkan/mod.rs.html))

**What that means for I5. [inferred]** A `VkRenderPass` keyed by the specific load/store ops, and
a `VkFramebuffer` keyed by the attachment views, are created the first time a given combination is
begun — which is inside the frame loop on the first frame that uses it. These are cheap metadata
objects, not shader compiles, but a non-zero *GPU resource creation* counter after frame one is a
violation as `docs/invariants.md` states it. The mitigation is the one
`docs/requirements/platform.md` already prescribes under *First-use work after the first presented
frame*: a warm-up pass, during load, that begins every attachment-and-load-op configuration the
puppet can reach. This is reasoning from the code's shape; nothing in wgpu documents a way to
pre-create a render pass or framebuffer directly, and that limitation is itself a finding.

**bgfx — lazy, and there is no way out. [primary]** In `src/renderer_vk.cpp`,
`getPipeline(uint64_t _state, ...)` builds a murmur hash over the render state
(`murmur.add(_state); ... const uint32_t hash = murmur.end();`), looks it up with
`VkPipeline pipeline = m_pipelineStateCache.find(hash);`, calls `vkCreateGraphicsPipelines` on a
miss, and inserts with `m_pipelineStateCache.add(hash, pipeline);`. `getPipeline` is called from
`RendererContextVK::submit`, guarded only by a one-entry memo of the previous draw's state. bgfx
exposes no API to pre-create a pipeline for a state vector; the only warm-up available is to
actually draw with every state combination before the first presented frame, which for a puppet's
blend, mask and composite combinations is both large and undiscoverable from the API.
([bgfx master src/renderer_vk.cpp, read 2026-11-26](https://raw.githubusercontent.com/bkaradzic/bgfx/master/src/renderer_vk.cpp))

**The web-technology option. [reported]** MDN's `createRenderPipelineAsync` page states it "is
generally preferable to use this method over `GPUDevice.createRenderPipeline()` whenever
possible, as it prevents blocking of GPU operation execution on pipeline compilation." A Mozilla
bug on browser UI freezes carries an engineer's comment that best practice is the async creators
"specifically to avoid this kind of jank" and that "without major changes, it is difficult to make
the synchronous versions avoid blocking all subsequent work." A separate Firefox bug traces a hang
to a D3D shader compile inside wgpu's DX12 backend. The decisive point is not that it is slow — it
is that the browser implementation chooses when compilation happens and Rigel2D cannot force it.
([MDN createRenderPipelineAsync](https://developer.mozilla.org/docs/Web/API/GPUDevice/createRenderPipelineAsync),
[Mozilla bug 1878449](https://bugzilla.mozilla.org/show_bug.cgi?id=1878449),
[Mozilla bug 1880415](https://bugzilla.mozilla.org/show_bug.cgi?id=1880415))

**Driver-level deferral affects every candidate equally. [inferred]** Some drivers do a final
specialisation at first bind rather than at pipeline creation. No abstraction can prevent this;
the mitigation is the same warm-up pass, and it is not a discriminator between options.

### 2. Headless per-frame counters with no GPU present

**The answer is the second one the brief offers: the runtime must emit its own command stream and
count that.** No candidate's null backend can supply these counters.

**wgpu's NOOP backend exists but cannot count draws. [primary]** `wgpu::Backends::NOOP` and
`Backend::Noop` are real. The documentation says it is a "Dummy backend, which may be used for
testing," that adapter enumeration always returns one noop adapter, that buffers can be created,
written, mapped and copied, and that command encoders can be created — but that "Render passes
and compute passes are not executed," "Textures may be created, but do not store any texels," and
"There are no compatible surfaces." It must be enabled explicitly through `NoopBackendOptions`,
whose `enable` field says the backend "stubs out all operations except for buffer creation and
mapping, so it must not be used when not expected."
([wgpu Backend enum](https://docs.rs/wgpu/latest/wgpu/enum.Backend.html),
[wgpu Backends](https://docs.rs/wgpu/latest/wgpu/struct.Backends.html),
[NoopBackendOptions](https://docs.rs/wgpu-types/latest/wgpu_types/struct.NoopBackendOptions.html);
all read 2026-11-26 against wgpu 30.0.2)

**Consequence. [inferred]** Draw calls, state changes, offscreen passes, vertices deformed,
binding evaluations, bytes uploaded and estimated shaded pixels cannot be recovered from a
stubbed-out backend, because the backend is where they would have been counted and it does
nothing. They must be derived from a command stream the runtime owns. This matches what
`docs/requirements/platform.md` already asks for — "computable from a frame's command stream
without a GPU present" — so the requirement was right and the abstraction does not weaken it.
`Backends::NOOP` remains useful as the *device* for headless runs, so that the resource-creation
counter and the whole load path exercise real code without a GPU.

**Every other candidate has an equivalent null device. [primary]** sokol_gfx has
`SOKOL_DUMMY_BACKEND`, which "replaces the platform-specific backend code with empty stub
functions" and is described in the header as useful for command-line tests. Qt RHI has a `Null`
backend, "a dummy backend that issues no graphics calls at all," selected with `QRhi::Null` and
`QRhiNullInitParams`. Vulkan directly has lavapipe and SwiftShader, which are software
implementations rather than stubs and so execute real passes, at a cost in CI time. None of these
changes the conclusion above: the counters live above the abstraction in every case.
([sokol_gfx.h](https://raw.githubusercontent.com/floooh/sokol/c0e0563/sokol_gfx.h),
[QRhi class reference](https://doc.qt.io/qt-6/qrhi.html),
[QRhiNullInitParams](https://doc.qt.io/QT-6/qrhinullinitparams.html))

**Because this criterion resolves the same way everywhere, it does not discriminate.** It does
change the design: the runtime's frame output is a command list it owns, and GPU submission is a
backend step below it. That is a requirement on the renderer's structure, decided here.

### 3. A queryable widget tree for structural UI assertions

The project's patterns, from `.claude/rules/testing.md`: bounding-box intersection, computed
colour and contrast ratio, computed size and position, focus order, accessible names and roles,
and scroll-width versus client-width.

| Toolkit | Mechanism | Geometry | Role / name | Computed colour | Headless |
|---|---|---|---|---|---|
| egui | `egui_kittest` over AccessKit | `bounding_box()` | `role()`, `label()` | No per-element query | Yes |
| Slint | `ElementHandle` + testing backend | `absolute_position`, `size` | `accessible_role`, `accessible_label` | Via `@testable` properties | Yes |
| Qt | `QAccessible` + `QTest` + `QWidget` | `geometry()` | Accessible interface | `palette()`, resolved style | Via offscreen platform plugin |
| Dear ImGui | Test Engine `ImGuiTestItemInfo` | `RectFull`, `RectClipped` | **None** | **None** | Yes |
| Iced | `iced_test` `Simulator::find` | Not exposed | Text match only | No | Yes |
| Masonry / Xilem | `masonry_testing::TestHarness` | Harness-dependent | AccessKit dependency present | No | Yes |
| Web shell | Playwright, DOM, CSSOM | `getBoundingClientRect` | Accessibility tree | `getComputedStyle` | Yes |

**egui. [primary]** `egui_kittest` describes itself as a "Ui testing library for egui, based on
kittest (an AccessKit based testing library)". A harness is built with `Harness::new_ui(app)`,
stepped with `run()`, queried with `get_by_label(...)` through kittest's `Queryable`, and nodes
expose their AccessKit data through `accesskit_node()`. The harness also checks by default that
input widgets have accessible names, controllable through
`Harness::builder().with_accessibility_check(false)`. kittest's `By` filter — "A filter for nodes.
The filters are combined with a logical AND" — supports `role`, `label`, `label_contains`,
`value`, `predicate` and `recursive`. Nodes are `accesskit_consumer::NodeRef`, which carries
`bounding_box()` ("Returns the node's transformed bounding box relative to the tree's container
(e.g. window)"), `raw_bounds()`, `transform()`, `role()`, `label()`, `is_focused()`,
`is_disabled()` and `is_hidden()`.
([egui_kittest 0.37.0](https://docs.rs/egui_kittest/latest/egui_kittest/),
[kittest By](https://docs.rs/kittest/latest/kittest/struct.By.html),
[accesskit_consumer NodeRef](https://docs.rs/accesskit_consumer/latest/accesskit_consumer/struct.NodeRef.html);
all read 2026-11-26)

**egui's two gaps, stated plainly.**

*Computed colour and contrast.* AccessKit carries no colour, and egui has no per-element style
query. **[inferred]** egui has no cascade: a widget's colour comes from the single `Visuals`
struct by widget kind and interaction state. So "computed colour" collapses to "the theme's colour
for this state", which a test can assert exhaustively over `Visuals` with no widget tree at all.
The browser pattern exists because CSS cascades and egui's styling does not. This reframing is
reasoning from the API's shape, not something egui documents, and it is wrong in exactly one case:
a widget painted with an explicitly overridden colour at the call site, where the override is
invisible to both the theme assertion and the accessibility tree.

*Overflow.* Scroll-width versus client-width has no AccessKit equivalent. **[inferred]** egui's
`ScrollArea` returns content size and inner rect from the app's own code, so the assertion is
writable but the test must reach into application state rather than query a tree.

*Custom-painted content.* **[inferred]** egui's accessibility tree contains only what egui
populates. A custom canvas — Studio's mesh editor, the timeline, the parameter graph — contributes
no accessible node unless its author calls `response.widget_info(...)` explicitly. For an editor
that is mostly custom canvases, criterion 3's coverage is therefore a function of authoring
discipline, not of the toolkit. **This is the single largest risk in this verdict** and the thing
most worth prototyping. Note that Qt and Slint have the same hole for custom-painted content; only
the web shell, where a canvas would be composed of real DOM elements, avoids it.

**Slint — the strongest native answer. [primary]** `ElementHandle` is found via
`find_by_accessible_label`, `find_by_element_id` or `find_by_element_type_name`, and exposes
`accessible_role`, `accessible_label`, `accessible_value`, `accessible_enabled`,
`accessible_checked`, `accessible_description`, `absolute_position`, `size`, `computed_opacity`,
`type_name`, `id`, `layout_kind`, `bases`, `query_descendants`, `visit_descendants`,
`testable_properties` and `testable_property_value`, plus simulated input including
`mock_single_click` for tests without an event loop. Methods return `None` when "the application
was built without debug info". The crate calls itself "preliminary API that we're developing to
enable different user interface (UI) testing scenarios" and its testing backend "simulates a
windowing system without requiring one, so no pixels are rendered."
([i-slint-backend-testing ElementHandle, 1.19.1](https://docs.rs/i-slint-backend-testing/latest/i_slint_backend_testing/struct.ElementHandle.html),
[C++ ElementHandle reference](https://snapshots.slint.dev/master/docs/cpp/api/classslint_1_1testing_1_1ElementHandle.html);
read 2026-11-26)

`testable_property_value` is what closes the colour gap: a `.slint` property marked `@testable`
can carry a resolved colour and a test reads it as a string. That is genuinely better than egui's
position, and it is the reason Slint is the named fallback.

**Dear ImGui — fails this criterion. [primary]** `ImGuiTestItemInfo` carries
`ImGuiID ID`, `char DebugLabel[32]` ("Shortened/truncated label for debugging and convenience
purpose"), `ImGuiWindow* Window`, `ImRect RectFull` ("Item Rectangle"),
`ImRect RectClipped` ("Item Rectangle (clipped with window->ClipRect at time of item
submission)"), `ImGuiItemFlags ItemFlags`, `ImGuiItemStatusFlags StatusFlags`, `ParentID`, `Depth`
and a `NavLayer` bitfield. Bounding-box intersection and size-and-position are therefore
available, and they are the patterns the generating case needed. Accessible names and roles,
focus order in the accessibility sense, and computed colour are not — the header never mentions
accessibility, and `NavLayer` is Dear ImGui's own keyboard navigation, not an accessibility tree.
([imgui_te_engine.h](https://github.com/ocornut/imgui_test_engine/blob/main/imgui_test_engine/imgui_te_engine.h), read 2026-11-26)

**Iced. [primary]** `iced_test`'s `Simulator::find` takes a `Selector`, and the `&str`
implementation "selects a widget by the text it contains"; `click` takes the same. No
accessibility selector appears in the official 0.14.0 crate. This is the weakest testing story of
any live option.
([iced_test 0.14.0](https://docs.rs/crate/iced_test/0.14.0))

**Masonry / Xilem. [primary]** `masonry_testing` provides a headless `TestHarness`, and Masonry
0.4.0 depends on `accesskit` 0.21.1. Masonry calls itself "a foundational framework designed for
building GUI libraries in Rust" and Xilem "an experimental high-level reactive framework for Rust
GUI applications". The architecture notes list accessibility info among things the harness is
meant to *eventually* emulate, which reads as intent rather than a shipped feature.
([masonry_testing 0.4.0](https://docs.rs/crate/masonry_testing/0.4.0),
[Masonry ARCHITECTURE.md](https://docs.rs/crate/masonry/0.4.0/source/ARCHITECTURE.md))

**Web shell. [inferred, from well-established platform behaviour]** Playwright plus
`getComputedStyle`, `getBoundingClientRect` and the accessibility-tree snapshot is the only option
where the project's existing patterns transfer with no translation. This is the one criterion the
web shell wins outright, and it is not enough to save it against criteria 1, 5 and 7.

### 4. Resident bytes and startup on the reference machine

**[unknown] for every native candidate.** No credible measurement of a non-trivial application
was found for Rust+wgpu+egui, Qt, Slint or D+Dear ImGui within this budget. Baseline empty-window
figures circulate widely and are, as the brief says, not useful evidence.

**Web shell, [reported] and weakly.** A Japanese blog summing resident memory across all processes
ten seconds after launch of a minimal app reported roughly 97–105 MB for Tauri over three runs and
212–216 MB for Electron, and noted that RSS double-counts shared pages. A team reporting on a
six-window macOS application measured about 172 MB for Tauri and 409 MB for Electron, attributing
the gap to Chromium renderer processes using roughly double WKWebView's. A Tauri issue records
that on Windows, where Tauri uses Edge WebView2, "Tauri using Edge WebView 2 had similar memory
usage with Electron, which makes sense given both are based on Chromium." Several 2026 comparison
sites report much larger gaps without stating a method; they are not usable.
([tauri#5889](https://github.com/tauri-apps/tauri/issues/5889),
[Hopp team write-up](https://dev.to/gethopp/tauri-vs-electron-performance-bundle-size-and-the-real-trade-offs-1el4),
[issoh.co.jp measurement](https://www.issoh.co.jp/md/tech/4114))

**Reading. [inferred]** Against the player's 700 MB, of which the reference puppet's
GPU-resident textures claim 100 MB, Electron's roughly 210 MB baseline leaves room on paper but no
headroom and little control, and on Windows Tauri converges to the same figure. This criterion
does not disqualify the web shell. Criteria 1, 5 and 7 do. No candidate can be ranked against the
3 s cold / 1 s warm startup budget from available evidence.

### 5. Allocation control in the frame loop

| Option | Zero CPU allocation per frame | GC pauses in an 8 ms p99 budget |
|---|---|---|
| Rust | Natural | None — no collector |
| C++ / Zig | Natural | None |
| D | Achievable with discipline, against the ecosystem | Stop-the-world, non-generational |
| JS in a web shell | Contorted | Minor collections land inside the budget |

**Rust. [inferred, from a documented language feature]** No garbage collector, explicit allocation,
and `GlobalAlloc` lets the runtime install a counting allocator — which makes
`docs/requirements/platform.md`'s per-frame *heap allocations* counter exact and nearly free rather
than something to be approximated. C++ can do the same by overriding `operator new`; the point is
that the counter the requirement demands is directly implementable, not that Rust is unique.

**egui is an immediate-mode toolkit and does allocate per frame.** egui's own documentation says a
full layout runs every frame, "for most cases you can expect egui to take up 1-2 ms per frame",
and that "egui only repaints when there is interaction (e.g. mouse movement) or an animation."
[primary] ([egui 0.37.0 crate docs](https://docs.rs/crate/egui/0.37.0)) **[inferred]** Against the
player's 4 ms solo CPU budget this would be 25–50% of the budget if the control surface repainted
every frame — which is why the split-window architecture matters. The control surface is a
different window with its own repaint cadence, idle when nothing is being adjusted, and the render
surface's frame loop contains no egui at all. Studio's figures are targets rather than
requirements, so 1–2 ms there is acceptable. If the control surface were in the same window as the
render surface, egui would be a problem; in the architecture above it is not.

**D. [reported]** A 2021 D mailing-list post reports informally that collections were unnoticeable
up to roughly a 300 MB heap and that stutter appeared beyond, and observes that any collection
longer than the frame interval causes a visible hitch.
([digitalmars-d, August 2021](https://lists.puremagic.com/pipermail/digitalmars-d/2021-August/318018.html))
**[inferred]** D's `@nogc`, `-betterC` and `GC.disable` make an allocation-free frame loop
reachable, but the standard library and the binding ecosystem allocate, so every dependency
becomes an audit. Against a 99th-percentile 8 ms budget with a hundred-megabyte-plus texture
working set, this is the wrong starting position.

### 6. Portability shape

The aim is macOS as a build target, with no Mac available to test on.

| Option | macOS path | Platform-specific code forced |
|---|---|---|
| Rust + wgpu + winit | Metal via wgpu's own backend | Packaging and signing only |
| Rust + Slint | Same, plus Slint's macOS backend | Packaging and signing only |
| C++ + Qt + Vulkan | MoltenVK, or Qt RHI's Metal backend | Vulkan-to-Metal layer, plus packaging |
| C++/Zig + sokol | sokol's Metal backend | Backend-conditional code at the sokol boundary |
| D | Whatever its bindings cover | Ecosystem-dependent, [unknown] |
| Web shell | WKWebView; Tauri transparency needs private API | Packaging, plus transparency workaround |

**[inferred]** wgpu's Metal backend is first-party and exercised by the same API surface as Vulkan
and DX12, so "a build target rather than a port" is the default outcome rather than something to
engineer. Qt is genuinely portable but Vulkan on macOS means shipping MoltenVK, which is a real
packaging item even though it is not reimplementation. Nothing here is disqualifying; this
criterion ranks rather than eliminates.

### 7. Transparent, decoration-free render surface with a real alpha channel

**winit. [primary, and weaker than one would like]** `WindowAttributes::with_transparent` says
"Sets whether the background of the window should be transparent. If this is `true`, writing
colors with alpha values different than `1.0` will produce a transparent window. On some platforms
this is more of a hint for the system and you'd still have the alpha buffer. The default is
`false`." `with_decorations` sets "whether the window should have a border, a title bar, etc."
**Neither method carries a per-platform note on that page**, so winit's documentation does not
state whether X11, Wayland, Windows or macOS honour the request.
([winit WindowAttributes](https://docs.rs/winit/latest/winit/window/struct.WindowAttributes.html),
read 2026-11-26)

**[unknown], and this is the gap most deserving of a spike.** That "more of a hint" sentence is
exactly the shape of claim this project marks rather than trusts. Transparency against a real
compositor on Wayland, X11 and Windows DWM — with a decoration-free window, correct premultiplied
alpha, and no per-platform branch in the runtime — was not established here and should be the
first thing a prototype proves. It is also the thing that, if winit fails it, most plausibly
reverses the verdict.

**Electron. [primary and reported]** Electron's docs state that setting `resizable` to true "may
make a transparent window stop working on some platforms" and that "the native window shadow will
not be shown on a transparent window"; the docs also note you cannot click through the transparent
area. A fix shipped in Electron 41.x for a Linux regression where transparent frameless windows
showed 1px borders, and for a longstanding issue where transparent windows on Linux "could show
smeared and glitched content as windows moved around." A user report describes transparency
appearing white with hardware acceleration enabled on Ubuntu. Independent of whether these are now
fixed, the pattern — transparency as a long-tail compositor bug surface on the exact platform tier
that blocks a release — is the finding.
([Electron custom window styles](https://electronjs.org/docs/latest/tutorial/custom-window-styles),
[electron#1335](https://github.com/electron/electron/issues/1335),
[electron#40515](https://github.com/electron/electron/issues/40515),
[backport PR 50605](https://releases.electronjs.org/pr/50605))

**Qt. [inferred]** `Qt::WA_TranslucentBackground` with `Qt::FramelessWindowHint` is long-established

## What would change this

**The spikes that would confirm or break the verdict**, in the order their failure would cost most:

1. **A transparent, decoration-free winit+wgpu window with correct premultiplied alpha, checked
   against a Wayland compositor, an X11 compositor and Windows DWM.** winit's documentation calls
   transparency "more of a hint" on some platforms and gives no per-platform notes. If this needs
   platform-specific code, the macOS-as-a-build-target premise weakens for every Rust option and
   Qt's maturity here becomes worth its other costs.
2. **An `egui_kittest` harness over a custom-painted canvas widget.** Can a mesh editor or a
   timeline be made to populate enough AccessKit nodes to carry criterion 3, and at what authoring
   cost? If the answer is "the editor's real surfaces are invisible to the harness", Slint's
   `@testable` properties and `ElementHandle` become worth its coupling and licence costs.
3. **A warm-up pass that creates every render pass and framebuffer configuration a puppet can
   reach, with the resource-creation counter asserted zero after frame one.** This is the concrete
   form of I5 under wgpu, and nothing in wgpu documents a way to pre-create those objects
   directly. If the warm-up cannot be made exhaustive from puppet data alone, I5 becomes
   unverifiable rather than merely demanding.

**What is likely to change.** wgpu's major version cadence is fast and `wgpu-hal`'s internals are
not a stable API — the render-pass and framebuffer caching described above is implementation
detail and could move. Slint's testing API describes itself as preliminary. Both should be
re-checked at the start of each development cycle, not trusted from this document a year out.

**What was not established.** Resident bytes and startup for any native candidate — criterion 4 is
effectively unanswered and the ranking does not rest on it. If it needs answering, the cheapest
route is to build the same small non-trivial application twice rather than to search for figures.

## Rejected options

**bgfx, as the GPU abstraction, in any language.** `getPipeline` creates `VkPipeline` objects
inside `submit()` on a state-hash cache miss, and bgfx exposes no way to force creation earlier.
This is I5 violated structurally, and the only warm-up available is to draw with every state
combination first, which is neither discoverable from the API nor enumerable from puppet data.

**Tauri or Electron over WebGPU or WebGL2.** Three independent failures. The implementation
decides when pipelines compile and WebGPU's own guidance is to use the async form because the
synchronous one blocks. A JavaScript frame loop cannot hold a zero-allocation budget and minor
collections land inside an 8 ms 99th-percentile window. Transparency on Linux is a recurring
compositor bug surface on a tier that blocks a release. It wins criterion 3 outright and that is
not enough.

**D.** A garbage collector against an 8 ms 99th-percentile budget and a hundred-megabyte-plus
working set, with the ecosystem pushing against `@nogc`; and in practice D here means Dear ImGui
— Inochi Creator is D with ImGui through bindbc-imgui — which fails criterion 3. Nothing about D
is disqualifying on its own and the incumbent ships with it; the combination of criteria 3 and 5
is what rejects it.

**Dear ImGui, with any language or GPU abstraction.** Its Test Engine gives item rects and IDs,
which covers bounding-box intersection and size-and-position, but it has no accessibility concept:
no roles, no accessible names, no focus order in the accessibility sense, and no per-element
colour. Criterion 3 is explicitly flagged as under-weighted in the project's existing documents,
and this is the option that would make the gap permanent.

**Iced.** `iced_test` finds widgets by contained text. Of the retained-mode Rust options it is the
weakest on the criterion that discriminates, and it offers nothing the others do not.

**Xilem and Masonry.** The right architecture — `masonry_testing::TestHarness` plus an AccessKit
dependency — under a framework whose own description is "experimental". Not a foundation for the
project's most consequential decision. Worth re-checking in a later cycle.

**Qt, with C++, over Vulkan.** Not rejected on capability — it has the strongest answer to
criterion 3 of any native option, genuinely computed rather than reconstructed, and the most
mature transparency story. It loses on the whole shape: MoltenVK on macOS against a
no-Mac-to-test-on constraint, C++ against Rust's free and exact per-frame allocation counter, and
a much heavier dependency than a project with no server, no networking and no localisation needs.
Reconsider if spike 1 or spike 2 above fails.

**Slint — the named fallback, not a rejection.** Loses on wgpu interop pinned behind
`unstable-wgpu-NN` feature flags to one wgpu major version, on carrying a second renderer
alongside wgpu in the editor, and on GPLv3 constraining the deferred plugin story. Its testing API
is better than egui's and that is the one thing that could bring it back.
